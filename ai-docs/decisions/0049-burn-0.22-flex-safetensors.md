# 0049. Migrate burn 0.21 → 0.22 (NdArray → burn-flex, BinFile → safetensors)

- **Status:** implemented on branch `burn-0.22` 2026-10-16 (see "Validation" for what was and was
  not verified).
- **Date:** 2026-10-16
- **Supersedes the "watch, no action yet" note in `gaps.md` §15 / the ADR 0023 note in `Cargo.toml`.**

## Context

burn 0.22 deprecates `burn-ndarray` ("use burn-flex, burn-cuda, burn-rocm, or burn-wgpu") and, in
the same release, removes the `Backend` type parameter from the whole API. somnus only ever ran burn's
CPU backend (ADR 0023 moved all GPU work to ORT/MIGraphX), so the choices were: stay on 0.21 and
accumulate drift, or migrate once while the surface is small (~250 generic-backend sites, 6 files).

## What changed

- **API:** `Tensor<B, N>` → `Tensor<N>`, `Linear<B>` → `Linear`, modules/optimizers lose their
  backend parameter. **Autodiff is a device property**: `Device::flex().autodiff()` replaces
  `Autodiff<NdArray>` (`TrainB`); `.inner()` keeps its name and meaning. `AdamWConfig::init()`
  returns a `ModuleOptimizer` (replaces `OptimizerAdaptor<AdamW, M, B>`). `NdArray::seed` →
  `Device::seed`. `into_scalar::<f32>()` / `try_to_vec::<f32>()` are explicitly typed.
- **Backend:** `burn-flex` (pure-Rust CPU, SIMD). Alternatives considered: staying on the
  deprecated `burn-ndarray` 0.22 (works, but removal is announced); CubeCL CPU/GPU backends (not
  needed — GPU stays on ORT, ADR 0023). **`burn`'s own dependency on `burn-flex` does not enable
  its `rayon` feature**, so a direct workspace dependency requests `["std","simd","rayon"]` (same
  trick the `burn-ndarray` line used). Without it flex silently runs single-threaded.
- **Persistence:** 0.22 has no `record` module / `BinFileRecorder`; weights are now safetensors via
  `burn-store` (`<stem>.safetensors`, plus the existing `.sizes` sidecar). Tensor names are module
  paths (`binding.region_0.weight`, `fc1.weight`, ...). Loading is `allow_partial`, and loaded
  params are re-wrapped as fresh autodiff leaves (`refresh_autodiff_state` / `Retrack`), because a
  loaded tensor carries no autodiff association.
- **Pre-existing bug fixed in the same change:** `wake_binding`'s GRU gates and `temporal_proj`
  were independently random-initialised and never synced from `binding` (ADR 0048 only copied the
  eight trained tensors), so a restored session's wake path used fresh random temporal weights and
  the exported ORT binding graph disagreed with the saved model. `BindingArea::copy_temporal_from`
  now aligns them at construction and on every `sync_wake_binding`.
- **0.22 fixed the `Linear::clone()` quirk** found during ADR 0048 (clones used to re-run the lazy
  random initializer). The regression pin was flipped; the explicit-copy seeding in
  `PerceptionModel::new` stays (harmless, no longer load-bearing).

## Existing snapshots

Every `weights.bin` / `decoder_weights.bin` under `/data/somnus/memory` is a 0.21 BinFile record, and
**none of them was loadable by `main` even before this change**: they all predate ADR 0048, whose
`wake_binding` field changed the positional record layout (load fails with `UnexpectedEof`).
They were converted by building the pre-0048 commit (`ea4364c^`) with a one-shot
`--convert-weights-to-safetensors` (kept out of the tree) and writing `*.safetensors` next to the
originals in `snapshot/` and `ab_binding_replay_freeze_heads_cpu/control/snapshot/`. Originals are
untouched. Restoring a converted snapshot needs `wake_binding` to be derived from `binding`
(automatic: `load_weights` syncs it).

## Validation

- **Numerical parity** (`crates/somnus-perception/examples/golden_dump.rs`, `scripts/compare_golden.py`,
  reference `research/burn-021-golden.json` generated on 0.21 *with the GRU fix applied*): real
  converted campaign weights (9821 units/region), fixed deterministic inputs, 8 ingests across all
  modalities, `measure_mse`, `infer_episode_outputs`, 5 NREM `replay_step`s. **0 differences at
  rtol 1e-3 / atol 1e-5**; losses and the MSE trajectory agree to ~5 digits; the ONNX weight files
  from `export_weights_for_onnx` agree to 4e-8 after training. 0.22 runs are bit-deterministic.
- **Gradient flow / seeding / round trip** tests added (`tests/seed_and_grad.rs`,
  `action::tests::proj_model_safetensors_round_trip_and_retrack`). Full workspace test suite,
  `clippy -D warnings` (default and `fine-metrics`) and `fmt` clean.
- **Live pilot:** see "Pilot results" below.

## What would invalidate this

A wall-clock regression in NREM/wake on flex vs ndarray (the pilot below is the check), or a
campaign-scale divergence the short golden run cannot show. The unvalidated surface: the decoder
(`ActionDecoder`) was verified only at the `ProjModel` level and by tensor names against the
converted file, not end to end with ORT sessions loaded; long-horizon (hundreds of cycles) training
behavior was not compared.

## Pilot results (2026-10-16, `--file clips/animation.mp4 --file-loop`, fine-metrics build, single machine)

**Arm 1, like-for-like restore (the one that matters).** The *original* pre-ADR-0048 build (0.21,
reads the original `weights.bin`/`decoder_weights.bin`) vs this branch (0.22, reads the converted
`*.safetensors`), same copied campaign snapshot, 2 sleep cycles:

| metric (cycle 1 / cycle 2) | 0.21 + original weights | 0.22 + converted weights |
|---|---|---|
| `per_region_mse` c1 | .0738 .0169 .0382 .0475 0 | .0751 .0172 .0381 .0521 0 |
| `mean_real_inference_mse` | .695 / .085 | .887 / .072 |
| `mean_output_mse_wake` | .152 / .164 | .173 / .159 |
| `wake_episodes` | 3276 / 120 | 3276 / 120 |
| `nrem_wall_ms` | 14420 / 1054 | 1546 / 728 |
| `rem_wall_ms` | 103100 / 7407 | 24550 / 3635 |
| `perception_total_ms` | 236300 / 1400 | 201100 / 3827 |
| peak RSS | 13.1 GB | 13.5 GB |

Converted weights restore and behave like the originals (per-region MSE within ~0.005 of each other,
identical episode counts, no NaN/step-error counters). The high `mean_real_inference_mse` in cycle 1
is this one-clip domain, not the conversion: the original build shows it too.

**Arm 2, fresh memory** (0.21 `main` vs 0.22, seed 7, 3 cycles): cycle-1 burn-bound phases
`perception_total` 43.8 s → 12.7 s, `nrem_wall` 13.8 s → 2.0 s, `perc_kwta` 6.9 s → 1.3 s,
`perc_symbolic` 12.6 s → 2.7 s, `measure_mse` 10× faster, `infer_episode_outputs` 8× faster. flex with
rayon+SIMD is much faster than ndarray on this workload.

**Deviations recorded (standing A/B policy):**
- *Total wall clock did not improve* (fresh-memory 488 s → 548 s; restore arm 523 s → 412 s): wake is
  real-time/clip-bound, so the burn speed-up shows in per-phase timers, not the total.
- *`encode_video` per-call time rose ~28 %* in fresh cycle 1 (104 → 134 ms): consistent with ORT's
  intra-op pool (half the cores, `onnx_thread_budget`) now competing with a rayon pool that scales
  better. Nothing sizes rayon's global pool to the other half of the cores (true on 0.21 as well; the
  doc comment claims a reservation that is not implemented). Follow-up Q14 in `gaps.md` §48.
- *Peak RSS +26 % in the fresh arm* (10.5 → 13.2 GB) but only +3 % in the restore arm: not
  understood; likely allocator/arena behaviour in flex on a growing model. Watch on long runs.
- `mean_output_mse` (REM probe) was 0 in both builds' cycle 1 but 0.056 in 0.22's cycle 2 vs 0 on
  0.21: probe sampling is timing dependent; not investigated.
- `nrem_stale_trace_skipped` fired 13.5k–15.6k times per 3-cycle run on both builds (so it is not a
  migration effect); it looks like most replay traces are skipped as stale, worth a look under §33.
